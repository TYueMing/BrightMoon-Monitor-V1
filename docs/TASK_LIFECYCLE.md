# Solo 灵动岛任务生命周期与持久化

本实现全部位于 `monitor_solo/`，不导入父项目，不访问 BrightMoon 登录、账户、注册表或后端。
来源仍使用 Solo 自己的 Codex、DeepSeek Harness、OpenCode 适配器；详情面板、声音选择、开关和
0～100% 透明度、1～10 分钟保留设置均保留。CodeAgent 仍是占位入口。

## 原因分析

原 Solo 只对终态建立内存计时，backend_id 更换会清空去重集合。暂停、失联或未确认停止不退场；
窗口读取异常时不更新 TaskSelection，且隐藏条件明确排除了 error，因此错误越持续，旧卡片越可能常驻。
程序重新启动后源日志/数据库仍保留同一任务，旧集合已不存在，于是又显示一次。

另外，OpenCode 进程被关闭后，SQLite 中的最后一行可能还是 running；不能据此持续显示健康执行。
固定的深蓝外缘又绕过了用户调色板，所以修改底色/透明度后仍有不协调的边线。

仅用五项动态数组不够。需要把来源事实、持久化显示记录和最多五项的可见任务列表分开。任务从 UI
移除后仍应读取来源，否则无法发现恢复、下一轮或新审批；收起不代表杀掉 Agent，也不会发送停止或授权命令。

## 状态和时间规则

1. 运行、等待模型、排队保持观察；健康的待授权/待回答不会被普通超时隐藏。
2. 暂停、stale、error、connection_error、cancellation_requested，从首次观察到该阶段起保留 60 秒。
   失联状态抖动、摘要补发、心跳、租约、UI revision 不延长它。停止请求不等于来源已停止。
3. cancelled 和 interrupted 从结束时间起保留 60 秒；没有有效时间则采用首次观察时间。
4. completed、failed、partial、blocked、budget_exhausted 使用 Solo 设置的 1～10 分钟。
5. 每项独立退场并释放显示名额，健康来源不受其他来源故障影响。所有项退场后灵动岛隐藏，主窗口和后台仍运行。
6. 读取抛错、返回无效数据或拒绝旧 revision 时，显示计时照常前进。读取失败清除缓存操作入口并标记连接失效。
7. 来源 worker 单次读取超过 30 秒，Hub 将缓存任务标记为连接异常；随后适用上述 60 秒期限。
   这是“来源读取卡住”的判断，不是按 Agent 多久没有输出文字判定失败。其他来源线程继续工作。

只读日志的静默阈值仍由适配器解释，例如 Harness 5 分钟、Codex 10 分钟没有落盘事件时提示无法确认状态。
时间到只影响显示，不声称来源进程已经死亡。OpenCode 本地服务不可达时给活动数据库行加 connection_error，
已落盘终态仍优先保留。

## 任务身份和恢复证据

`monitor/src/task_identity.py` 将 app_id、数据集 monitor_scope、逻辑任务标识、执行轮次组合取摘要。
逻辑标识默认 run_id，也允许适配器用 monitor_task_id 统一日志与在线连接别名；轮次依次采用
completion_id、turn_id、规范化 started_at。单纯改后端 UUID、启停开关或切换连接模式不清空历史。
数据路径规范化后取摘要，不将明文路径写入显示记录；修改数据路径会切换数据集作用域。

目前自动发现的空路径与显式目录配置属于不同作用域，目录别名/符号链接不合并；改成同一物理目录的
另一种写法可能产生一次新的首次观察。来源必须提供稳定的执行轮次；不允许把轮询时间当 started_at。

收起的非终态任务只在这些情况下重新显示：

- paused 明确恢复为执行状态，且事件时间没有倒退。
- 来源发布未见过的真实执行证据；单纯连接成功不能唤醒。
- 出现新的有效审批/问题，或来源仍明确提供对应操作。只读旧授权日志的重连不会自动重新弹出。
- 同一会话产生新的 completion_id/turn_id/开始时间，视为新的执行轮次。

通用回退证据包含任务、步骤、调用 ID 和状态及数值用量。若适配器提供 monitor_activity_id，则以它为准；
空值表示尚无新执行证据，不回退到重连时部分补载的旧工具列表。Codex 使用实际执行通知/日志的确定性摘要，
DeepSeek 使用允许列表内的持久化执行事件 seq，OpenCode 使用当前轮次消息与 part 的 ID/修改时间。
标题编辑、连接/租约更新不产生执行证据。比水位更旧的事件不能唤醒；失联期间补载的内容先作为已见基线。

同一轮次已有最终结果后，旧的 running 记录与补载工具不能使它复活。继续工作需有新的轮次身份。
有效交互请求仍优先保留，以支持 Harness 在原轮次结束后等待补充回答的场景。

## 不登录的持久化

`monitor/app.py` 创建 `DisplayHistory.for_data_root(SettingsStore.root)`，默认位置为
`monitor_solo/data/display_history.sqlite3`。整个文件夹可复制；没有账户目录和父工程路径依赖。
启动仍使用 Solo 自己的单实例锁，数据库操作在 UI 线程完成，不由来源线程直接写入。

SQLite `display_receipts` 以身份摘要为主键，存储阶段、进入时间、已退场标志、是否见过终态、执行证据摘要、
事件水位和本次启动的随机显示会话 ID。它不记录用户名、提示词、原始输出、工具参数或明文工程路径。
没有日期清理和数量清理；内存只缓存最近约 8192 项，仍在来源快照中的项和未保存项不强制移出。
内存淘汰只移出缓存，数据库记录不删除，下次需要时按身份查询。文件大小随历史任务数增长。

普通执行证据最多每两秒批量写一次，终态、进入退场阶段和实际收起立即事务提交；正常关闭强制保存并关闭数据库。
没有变化的心跳不写盘，持续存在的记录最多每天更新一次观察时间。SQLite 事务失败保留原数据、内存记录和待重试项。
保存/读取故障在主窗口提示；不可读或损坏数据库不会被悄悄删除覆盖，当前进程降级为内存去重。
跨启动去重依赖数据库可读写；硬件损坏、丢弃 data 文件夹或写盘失败无法承诺历史去重。

## 再次启动的具体行为

- 从上一显示会话读取的完成、失败、停止、失联、暂停、已退场记录直接保持收起，即使上次的保留时长尚未走完。
- 上次还在执行、这次首次重新读取时已经结束的已知任务，也静默记为结果，不重新弹出。
- 上次暂停但这次已明确恢复，或收起后出现新进展、新轮次、有效交互，仍正常显示。
- 上次仍在执行且本次来源继续确认活动的任务可以继续显示；历史记录不是永久屏蔽所有见过的 ID。
- 从未监控过的任务由来源的初始历史过滤和本地结束时间规则共同判断；本功能不追溯此前未观察到的全部历史。

完成音在过滤退场记录后触发，按执行轮次去重。启动先收到空快照、随后才收到旧完成记录，也保持安静；
同一会话的新轮次在本次运行期间完成仍能提示。定时隐藏继续观察，不等于关闭来源设置开关。

## UI 外观修复

外缘、主体、内侧描边都经过当前背景色调色板。外缘由底色与对比色混合，内侧描边同样按对比色生成，
不再混入固定深蓝或当前任务状态色；状态蓝/黄/红/绿继续体现在对应任务圈。Tk 的窗口 alpha 同时作用于
所有边缘和内容，胶囊、第二层和第三层使用相同规则。完全透明时可以从主窗口个性化页面恢复。

关键状态即时提交、内存淘汰不丢磁盘历史、跨启动静默结果与声音、文件夹搬迁和原生 Tk 的实际边缘颜色/alpha。

主题实拍预览位于 [preview/solo-theme-lifecycle.png](../preview/solo-theme-lifecycle.png)，覆盖白色、蓝色胶囊
与 50% 不透明度的紫色展开卡片；可运行 `python tests/render_recovery_preview.py` 重新生成。

主要实现位置：

- `monitor/src/display_history.py`：独立 SQLite 记录、缓存、重启恢复和写盘失败处理。
- `monitor/src/task_identity.py`：稳定身份、轮次与实际执行证据。
- `monitor/UI/task_lifetime.py`、`task_selection.py`：逐项期限、过滤、恢复与焦点。
- `monitor/UI/island.py`、`common_model.py`、`window_state.py`：异常读取、声音、隐藏、主题和一致状态集合。
- `monitor/src/source_hub.py`：数据集隔离、来源读取卡住的诊断及操作撤销。
- `monitor/app.py`：绑定 Solo 的 data 目录、正常退出提交和存储错误提示。
- 各来源的 projection/interactions/bridge/adapter：发布真实执行证据、逻辑任务身份、OpenCode 连接健康。

父项目 `monitor/` 的代码未修改；Solo 中的这些文件是本地实现，不是指向父项目的导入或链接。
